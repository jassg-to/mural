### Layer: Media decoding (`video.go`)
- [x] Step 1: Create `video.go` with the `Video` struct and `NewVideo()`, probing `ffmpeg` and `ffprobe` via `exec.LookPath`; log one line and return a disabled `*Video` when either is missing. Done when `NewVideo()` compiles and returns a non-nil `*Video` on a machine with and without ffmpeg installed.
- [x] Step 2: Add the `videoInfo` struct and the pure `parseProbeOutput([]byte) (videoInfo, error)`. It must parse **exactly the JSON shapes pinned in Architect.md → *ffprobe contract***, all four of which are transcribed from real ffprobe 8.1.2 output: `width`/`height` decode as JSON numbers, `codec_name` and both `duration` fields as JSON strings needing `strconv.ParseFloat`, unknown extra top-level keys (`programs`, `stream_groups`) ignored, `streams` possibly an empty array, and — for the corrupt-file case, where ffprobe prints a bare `{}` — `streams` and `format` possibly **absent entirely**, which must yield a clean error rather than a nil-dereference. Duration priority is `streams[0].duration` first, `format.duration` only as fallback — **never** `format.duration` alone (blocker B2, confirmed by measurement: a real 3 s-video/5 s-audio clip reports `format.duration` of 5.000000 against a true video length of 3.000000). Reject: absent or empty `streams`, `codec_name != "h264"`, non-positive `width`/`height`, no parseable duration from either source, non-positive duration, malformed JSON. Done when it returns a populated `videoInfo` for valid JSON and a distinct wrapped error for each rejection case, and never panics.
- [x] Step 3: Add `(*Video) probe(path string) (videoInfo, error)`. Command, verified against ffprobe 8.1.2: `ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,width,height,duration:format=duration -of json <abs-path>`. **`stream=duration` must be in that list** — omitting it is what forced Phase 2 onto `format.duration` and caused blocker B2. Resolve `path` through `filepath.Abs` first (warning W2 — `content/` is a network-writable Samba share and `./mural .` yields bare names; verified that a file named `-dash.mp4` fails with `Missing argument for option 'dash.mp4'`). **Do not add a `--` terminator** — ffmpeg has none and `ffmpeg -i -- file` fails with exit 254; `filepath.Abs` alone is sufficient. Run under a **10 s** `context.WithTimeout` and reap the process (blocker B5 — `CombinedOutput`/`Output` wait implicitly, which satisfies this). **Check the exit code *and* parse the output**: a corrupt file exits 1, but an audio-only file and an HEVC file both exit **0** and are rejected purely at parse time. Return an error immediately when the `Video` is disabled. Delegate all parsing to Step 2. Done when it returns metadata for a real MP4, an error when disabled, an error on ffprobe failure, and an error rather than a hang on a file that wedges ffprobe.
- [x] Step 4: Add the pure `fitDimensions(srcW, srcH int, winW, winH float32) (int, int)` helper — contain-fit using the same `math.Min` rule as `decodeAndFit` (`slideshow.go:108`), rounded to even values with a minimum of 2. Done when it returns exact even dimensions for landscape, portrait, and square sources.
- [x] Step 5: Add `(*Video) firstFrame(path string, width uint) (image.Image, error)` running `ffmpeg -v error -i <abs-path> -frames:v 1 -f image2pipe -vcodec png -` (verified against ffmpeg 8.1.2 — yields a ~25 KB PNG on stdout, exit 0) and decoding stdout via `image.Decode`, then resizing to `width` with `resize.Resize(width, 0, src, resize.Lanczos3)` to match `loadThumbnail` (`slideshow.go:49`). Same `filepath.Abs` handling as Step 3, and likewise **no `--` terminator**. Run under a **15 s** `context.WithTimeout` and reap the process (warning W4 + blocker B5 — this runs synchronously inside `scanSlides`, which runs inside `Reload`, which runs at schedule turn-on; an unbounded hang here stalls the display coming on). Done when it returns a non-nil image of the requested width for a real MP4, an error otherwise, and returns within the timeout on a wedged input.
- [x] Step 6: Add `(*Video) play(ctx context.Context, path string, w, h int, onFrame func(image.Image), onDone func(error))` running `ffmpeg -v error -re -i <abs-path> -an -vf scale=<w>:<h>,fps='min(30,source_fps)' -f rawvideo -pix_fmt rgba -`. The cap is the Phase 3 throughput ruling (Architect.md → *Frame delivery*). **Use the `min(...)` expression, not a bare `fps=30`** — the `fps` filter is a rate converter, not a cap, and measurement showed `fps=30` *duplicating* a 25 fps source up to 30 fps, raising pipe traffic 20 % on the most common signage frame rate. Verified: with `min(30,source_fps)` a 25 fps source passes through at 75 frames and a 60 fps source clamps to 60 over 2 s. Read exactly `w*h*4` bytes per frame with `io.ReadFull` into an `*image.RGBA` whose `Stride` is `w*4`, and invoke `onFrame` on the caller's goroutine — the byte contract is verified exact (27 648 000 bytes = 90 × 320×240×4, zero remainder). Add a comment noting that Go's `image.RGBA` is alpha-premultiplied while ffmpeg's `rgba` is straight alpha — harmless here only because video carries no alpha and ffmpeg emits `A=255` (note N2), so nobody "fixes" it later. Deliberately **no timeout** — clips are legitimately arbitrarily long; `ctx` cancellation is the only stop signal. Call `onDone(nil)` on clean EOF (`io.EOF` on a frame boundary) and `onDone(err)` otherwise, including a short/truncated final frame. **Must `Wait()` the process after the read loop ends, on every path including cancellation and error** (blocker B5 — `StdoutPipe` does not wait implicitly, and one zombie per slide over months of kiosk uptime exhausts the process table).

  **stderr must be drained, never left in an undrained pipe** (warning V14). `-v error` means ffmpeg *will* write on stderr for exactly the malformed inputs this code exists to survive; if stderr is a `StderrPipe()` that nothing reads, ffmpeg blocks on write once the 64 KB pipe fills and the player wedges — self-inflicting the precise failure the watchdog exists to catch. Assign `cmd.Stderr` to a **bounded** `io.Writer` (a small ring or a `bytes.Buffer` behind an `io.LimitedWriter`, a few KB is ample): Go's `os/exec` spawns its own copier goroutine for a non-`*os.File` writer, so it drains continuously and cannot block. Include the captured text in the `onDone(err)` message.

  **Reuse frame buffers** (warning V8). Allocating a fresh `*image.RGBA` per frame is ~250 MB/s of garbage at 1080p30 — on a Pi the GC cost shows up as CPU and jitter even while RSS looks flat, so Step 22b's flat-RSS check alone would not catch it. Keep a small free-list of 2–3 identically-sized `*image.RGBA` and recycle a buffer only once the `fyne.Do` drain that consumed it has released it back; never write into a buffer the UI may still be reading. Two buffers is the minimum (one displayed, one filling); three removes any stall if a drain runs long.

  Done when a clip plays to completion, a cancelled context terminates the ffmpeg process promptly, `ps` shows no accumulated zombies after a hundred play/cancel cycles, a clip that makes ffmpeg chatter on stderr does not wedge, and allocation per frame is flat under `go test -benchmem`.

- [x] Step 13: Add the video branch to `show`: display the first-frame thumbnail, create a cancellable context, store it via `playerCancel`, and run `vid.play` in a goroutine. - [x] Step 14: Wire playback completion to advance. `onDone` fires on the **playback goroutine**, so the advance must be marshalled through `fyne.Do` — `show` is documented "must be called from the Fyne main goroutine" (`slideshow.go:208`) — and must re-check both the generation captured at show time **and `s.paused`** before advancing (blocker B4: the deleted ticker goroutine had an explicit `if s.paused { return }` at `slideshow.go:276`; without it a race between `pause()` and a clean ffmpeg exit un-blanks a screen the schedule just turned off). **A video slide advances at `max(end-of-stream, probed duration)` — the probed duration governs and EOS merely reports that ffmpeg finished.** This inverts Phase 2's "advance on EOS" rule, because measurement shows `-re` finishes reliably and substantially early: a 3.000 s clip reached EOS at 2.42 s across three runs, a 2.000 s clip at 1.51 s — roughly half a second early, every time, on every clip. Advancing on EOS would cut *every* video short, not just an edge case, violating the Analyst rule "must not advance before the video's actual duration has elapsed" universally. The last frame simply stays on screen for the final ~0.5 s, which reads as an ordinary freeze-frame ending. Arm `scheduleAdvance(duration + 2s)` as a watchdog when a video slide is shown so a wedged ffmpeg cannot stall the rotation; since EOS reliably arrives early, this now fires only on a genuine wedge. Apply the **minimum re-arm floor** (warning W5): when a video advances to itself (`len(slides) == 1`), defer so consecutive playback starts are at least 1 s apart — this is not a duration clamp, the clip still plays in full, it only stops a sub-second lone clip from spawning ffmpeg dozens of times a second. Done when a video advances no earlier than its probed duration (measure it — a 3 s clip must occupy the screen for ≥3 s, not 2.42 s), a killed ffmpeg process still advances after the grace period, pausing mid-playback never advances, and a 0.2 s lone video does not spin the CPU.
