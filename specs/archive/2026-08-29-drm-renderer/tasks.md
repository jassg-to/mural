- [x] Step 8: Create `drm.go` — `DRMRenderer` struct and `OpenDRMRenderer(devicePath string) (*DRMRenderer, width, height int, err error)`: acquire master, enumerate the connected connector, pick its mode via `pickPreferredMode`, allocate and map two dumb buffers. Each acquisition (fd open, `SET_MASTER`, buffer 1 create/map, buffer 2 create/map) gets its cleanup deferred immediately after it succeeds — not batched at the end — so a failure partway through (e.g. buffer 2's map fails after buffer 1 already succeeded) unwinds everything acquired so far via a named-error return path, per `CLAUDE.md`'s "use `defer` for cleanup immediately after acquiring the resource." A partial failure that leaks DRM master is exactly the failure mode this design exists to avoid.
- [x] Step 9: In `drm.go`, implement `(*DRMRenderer) Present(frame *image.RGBA) error` — `nil` frame composites black via `compositeLetterboxed`, converts via `rgbaToXRGB8888` into the back buffer, page-flips, waits for the flip event, swaps front/back. A page-flip failure because no display is attached (HDMI unplugged) is returned as an ordinary error like any other page-flip failure — no special detection, no panic, no retry loop inside `Present` itself; the caller (run loop) logs it and moves on, and a later reconnect is picked up reactively the next time `Present` is called for a slide change.
- [x] Step 10: In `drm.go`, implement `(*DRMRenderer) Close() error` — unmap and destroy both dumb buffers, drop master.
- [x] Step 11: Create `vt.go` — install `SIGUSR1`/`SIGUSR2` handlers (`VT_SETMODE(VT_PROCESS)` on the controlling tty) that drop/reacquire `DRMRenderer`'s master and re-set the mode on VT switch-away/back.
- [x] Step 12: In `vt.go`, install `SIGTERM`/`SIGINT` handling that calls `DRMRenderer.Close()` and restores the console to text mode (`KDSETMODE(KD_TEXT)`) before exit. (Reconciled with Architect.md's Approach section and Step 21, which are more specific about sequencing: `vt.go`'s handler calls `cancel()` — the same shutdown mechanism `NavQuit` uses — and exposes `RestoreConsole()`; `main.go` calls `renderer.Close()` then `vt.RestoreConsole()` after `Run()` actually returns, so console restore never races the still-active DRM calls a mid-shutdown run loop could still be making.)

### Spontaneous: sdd-eval Findings (Phase 5, fresh-context)

`specs/drm-renderer/EvalReport.md` ran a fresh-context Phase 5 evaluation against `Analyst.md`/`Architect.md`/`tasks.md` and the code on disk, independent of everything above. Verdict: **FAIL** — 5 ❌ findings (3 actionable code defects, 2 decisions for the user), 8 ⚠️ warnings. Each ❌/⚠️ was independently re-verified against the actual source before any fix, not taken on faith.

- [x] **F2 (confirmed, fixed) — `install.sh`'s crash-loop guard was unreachable dead code.** `tty1-guard.sh` used `exec ./mural`, which replaces the shell process — so the "waiting 30 seconds" banner and the `.bashrc` re-invocation after it could never run. Concrete consequence: a clean Escape-quit (`NavQuit` → `cancel()` → exit 0) made `.bashrc`'s `if bash tty1-guard.sh; then exit 1; fi` true, respawning mural instantly and forever with no throttle and no way to reach a shell — exactly Analyst.md's "must not hold the console hostage" edge case, and worse than the crash case (a non-zero exit), which *did* fall through correctly. Fix: dropped `exec`, matching the pre-rewrite script's own behavior (`git show 9942bc4:install.sh` also called `startx` without `exec`) and Step 28's literal instruction to keep the banner/sleep/`.bashrc` shape unchanged.
- [x] **F3 (confirmed, fixed) — `drm.go`'s `waitForFlipEvent` could hang the run loop forever.** An unbounded blocking `unix.Read` with no timeout and no `ctx` awareness, called synchronously from the single run-loop goroutine. If a page-flip is accepted but its completion event never arrives — HDMI unplugged, or `vt.go`'s `SIGUSR1` handler racing a `DROP_MASTER` before the flip completes — the read blocks indefinitely: no nav keys, no advance timer, no VT reacquire, and `ctx.Done()` can't break a blocked syscall, so not even `SIGTERM` would work. A hang is strictly worse than the busy-loop Architect.md explicitly rules out for this exact scenario. Fix: `waitForFlipEvent` now takes a `timeout time.Duration`, uses `unix.Poll` with a bounded wait (`pageFlipTimeout = 2 * time.Second`, a generous margin over one ~16ms vsync interval) instead of a raw blocking read, and returns an ordinary timeout error — handled by the run loop exactly like any other `Present` failure — rather than hanging.
- [x] **F4 (confirmed, fixed) — data race on `DRMRenderer.front`.** `vt.go`'s `WatchSwitches` goroutine reads `r.buffers[r.front]` on `SIGUSR2` (VT reacquire) while `drm.go`'s `Present`, on the run-loop goroutine, both reads and writes the same field — a plain `int`, no mutex, no atomic, no channel hand-off. Undefined behavior under the Go memory model regardless of whether it's ever visibly hit on real hardware (the eval's own note: 0% test coverage on both files means `go test -race` structurally cannot catch it; only on-hardware exercise could, and Step 33's single quiet `chvt` cycle wasn't enough to hit the window). Fix: `front` is now `atomic.Int32`, `Load()`/`Store()`'d at both call sites (`drm.go`'s `Present`, `vt.go`'s `WatchSwitches`).
- All three fixes re-verified: `go vet .`, `gofmt -l .`, `go test -race .` (all clean), plus both `go build .` (amd64) and the `GOOS=linux GOARCH=arm64` cross-build succeed.
